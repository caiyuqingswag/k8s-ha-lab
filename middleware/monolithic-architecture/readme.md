# 存储方案说明（基于 NFS）

本 README 用于说明当前系统采用 **NFS（Network File System）** 作为共享存储方案的原因与基本架构设计。该方案适用于**单体架构或小规模集群环境**，强调 **简单、易部署、低成本、易维护**。

---

## 一、方案背景

当前系统整体规模较小，所有中间件与业务数据总量不超过 **600GB**，主要组件包括：

* MySQL
* Redis
* MinIO
* InfluxDB
* RabbitMQ

在该规模下，我们对存储系统的核心诉求是：

* 简单可靠
* 成本可控
* 易于部署
* 易于维护
* 支持多节点访问

因此，我们选择使用 **NFS 作为共享存储方案**。

---

## 二、为什么选择 NFS

NFS 是一种成熟、稳定、广泛使用的网络文件系统，适合中小规模环境。

### NFS 的主要特点：

* 共享存储：多台服务器可同时访问同一份数据
* 部署简单：无需复杂的集群组件
* 成本低：无需专用存储设备
* 运维友好：易于监控与维护
* 兼容性强：几乎所有 Linux 系统原生支持

对于当前业务规模，NFS 可以满足稳定性和可用性的基本需求。

---

## 三、系统中各组件的存储方式

| 组件          | 存储方式     |
| ----------- | -------- |
| MySQL       | NFS 挂载目录 |
| Redis (AOF) | NFS 挂载目录 |
| InfluxDB    | NFS 挂载目录 |
| RabbitMQ    | NFS 挂载目录 |
| MinIO       | NFS 挂载目录 |

---

## 四、部署模式说明

在 Kubernetes 或传统部署环境中：

* NFS 服务器提供统一的共享目录
* 所有有状态服务挂载该共享目录
* 数据集中存储，便于管理和备份

该模式具备以下优点：

* 数据集中管理
* 迁移简单
* 备份方便
* 运维复杂度低

---

## 五、适用范围

NFS 方案适用于以下场景：

| 条件        | 是否适合 |
| --------- | ---- |
| 数据量 < 1TB | ✅    |
| 单体应用      | ✅    |
| 小规模集群     | ✅    |
| 对一致性要求不高  | ✅    |
| 对自动容灾要求不高 | ⚠    |
| 核心金融级系统   | ❌    |
