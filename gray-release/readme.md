# 灰度发布（Canary）决策指南

本 README 用于帮助研发在每次发版前，快速判断：

> 当前版本是否需要使用普通灰度（仅后端灰度），还是需要**前后端强绑定灰度**。

目标是：

* 降低发布风险
* 避免过度设计
* 规范发布决策流程
* 让灰度成为“常规操作”而不是“高成本操作”

---

## 一、核心结论（先看这个）

### 90% 的版本，只需要：

> ✅ **后端灰度即可（前端全量，后端 v1/v2 分流）**

只有在**接口存在破坏性变更**时，才需要：

> ⚠️ 前后端强绑定灰度

---

## 二、两种灰度模式说明

### 1️⃣ 普通灰度（推荐）

结构：

```
前端：100% 新版本
后端：v1 95% + v2 5%
```

适用场景：

* 新增字段
* 新增接口
* 新增可选参数
* 新增功能开关
* 性能优化
* Bug 修复

特点：

* 配置简单
* 资源消耗小
* 回滚快
* 运维成本低

---

### 2️⃣ 前后端强绑定灰度（高级）

结构：

```
用户 → v1 前端 → v1 后端
用户 → v2 前端 → v2 后端
```

适用场景：

* 删除字段
* 字段重命名
* 字段类型变更
* 返回结构大改
* 协议版本升级
* 完全不兼容的接口变更

特点：

* 配置复杂
* 成本高
* 运维难度大
* 风险更高

---

## 三、发版前判断清单（最重要）

在每次发版前，请研发或产品确认以下问题：

### 如果以下全部为“否” → 使用普通灰度

| 问题            | 是 | 否 |
| ------------- | - | - |
| 是否删除了接口字段？    | ⬜ | ⬜ |
| 是否重命名了字段？     | ⬜ | ⬜ |
| 是否改变了字段类型？    | ⬜ | ⬜ |
| 是否改变了字段含义？    | ⬜ | ⬜ |
| 是否修改了返回结构？    | ⬜ | ⬜ |
| 是否要求前端必须同步升级？ | ⬜ | ⬜ |

如果以上全部为「否」：

> ✅ 使用 **普通灰度**（仅后端灰度）

---

### 如果以下任意一项为“是” → 考虑强绑定灰度

| 问题             | 是 | 否 |
| -------------- | - | - |
| 新前端是否无法调用旧后端？  | ⬜ | ⬜ |
| 旧前端是否无法调用新后端？  | ⬜ | ⬜ |
| 接口协议是否发生破坏性变更？ | ⬜ | ⬜ |
| 是否存在字段完全不兼容？   | ⬜ | ⬜ |

如果以上任意一项为「是」：

> ⚠️ 需要评估 **前后端强绑定灰度**

---

## 四、为什么默认不使用前后端绑定灰度？

因为它会带来：

* 双倍资源消耗
* 双倍配置成本
* Cookie/Session 绑定复杂
* 缓存难管理
* 排错困难

只有在**强不兼容场景**下，才值得承担这些成本。

---

## 五、推荐的发布流程（标准化）

1. 研发提交版本说明
2. 运维根据本清单判断灰度模式
3. 默认使用普通灰度
4. 从 5% 开始放量
5. 监控指标
6. 无异常逐步放量至 100%
7. 删除旧版本

---

## 六、术语说明

| 术语    | 含义            |
| ----- | ------------- |
| 普通灰度  | 仅后端 v1/v2 分流  |
| 强绑定灰度 | 前后端 v1/v2 强绑定 |
| 向后兼容  | 新版本不影响旧调用     |
| 破坏性变更 | 会导致旧客户端不可用    |

---

## 七、结论

灰度发布的目的不是“炫技”，而是：

> **控制风险，而不是制造复杂度。**

默认应使用：

> ✅ 普通灰度（只灰度后端）

仅在必要时才使用：

> ⚠️ 前后端强绑定灰度

---

本规范适用于当前生产环境，后续可根据业务复杂度进行升级。
